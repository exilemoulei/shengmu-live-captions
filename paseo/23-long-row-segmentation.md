# 23 · 超长 ASR 行切句（连续讲话不分段）

覆盖 `05` §5.A 的修复方向。`plan.md` 原来记的「顶满 70vh」已过时：浮层各槽位早已是尾部对齐的窗口，真正的损失在翻译链路。

## 1. 要解决什么

连续讲话时 WLK 一整段只出一行（`Gq2r7x5qgmg-poe-24m00-26m00.wav` 约 2600 字符，`WIuIdulr-K0-poe-30m45-32m45.wav` 约 2200 字符）。

根因（读 WhisperLiveKit 0.2.26 源码 `tokens_alignment.py` 的 `get_lines`）：关闭说话人分离时，行**只在 `Silence` token 上结束**，与标点无关。游戏音效让 VAD 一直判有声时，这一行不会结束。`--buffer_trimming` 裁的是音频，不是行，所以调它没用。

真机（下文 §5）上后果比原记录严重：

- 每次重译都重发整行，发送字符是终态的 44~68 倍。
- 约 55 s、行长约 1250 字符时，译文超过输出上限（`The translation API output was cut off`），**此后不再发任何请求**，还剩 65 s 的中文停在半句。
- 历史里这一行 2571 字符英文只有 338 字中文，并记为失败。

另一个之前没记录的问题：`_prune` 同样裁 `current_line_tokens`。行活过 `--retention-seconds`（当前 300）后，开头的词被丢弃，行的 `start` 每帧都变，而行 id 由 `start` 推出，于是**每帧都是一行新字幕**。用 `--retention-seconds 30` 在真实 WLK 上复现：120 s 内出现 72 个行 id、最大请求 1387 字符。

## 2. 为什么在客户端切

- WLK 是维护者的 fork，没有切行参数；改参数要跑样本对比，而且只解决 WLK。
- 客户端切同时覆盖百炼和 Chrome 识别（它们也可能给出很长的一行）。
- 流水线其余部分（合句、阶段译文、历史、SRT）本来就能处理「一串短行」，所以把长行变成一串短行，不用改下游。

只在 API 模式切：server 模式的译文按 WLK 的行对齐，无法分配给切开后的各段。这种长行仍靠浮层的尾部窗口显示。

## 3. 怎么切（`lib/caption-segment.js`）

`cutSentences` 从前往后扫，每段不超过 `FRAGMENT_MAX_CHARS`（180），依次优先：

1. 句末标点，且下一个词不是小写开头。实测 `really good. for like a few days.` 这种句中句号很常见（一段 2600 字符里有 16 处），来自 Whisper 的分块，靠后一个词的大小写区分。`Mr.`、`U.S.` 这类缩写不算句末。
2. 累计到 `SEGMENT_CLAUSE_MIN_CHARS`（120）后的任意子句标点。
3. 超长时强切，回看后 40%：子句标点 > 连接词（and/so/because…）之前 > 不以虚词结尾且不拆开 `Path of Exile` 这类 `of` 术语的词。`WIuIdulr` 样本里有一段 2144 字符完全没有标点，全靠这一档。

**不变量：追加文本不会移动已有的切点**（有测试逐词验证），行 id 依赖这一点。第一段沿用原行 id，之后是 `<id>#<序号>`。不超长的行原样通过，不增加任何字段。

其它取舍：

- `mergeCaptionFragments` 不再把 `and ...` 粘回 ≥120 字符的段，否则它长到 11 个词又掉下来，白白重译一次。
- 时间：识别器只给整行的起止，且止点每帧在动。行不再增长时，沿用它最后一帧的止点（当时恰好是最后一个词的结束时间），已完成的行因此不会每帧重写历史。一次到达的长文本按字符占比估算。合并时记录 `segmentTail`（单元以哪个切分行结尾），它决定单元的止点。
- 被裁剪的行（§1）：新行的起点早于旧行的止点、id 未见过、且文本能从某处起与旧行完全接上，才算同一行，继续用旧 id。只比较前 48 个字符不够，重复的话会定位错。比较文本而不是时间，因为各段起点是估算值：实测行被裁到段边界时，新起点（2.28）比该段估算起点（2.29）还早。
- 百炼和 Chrome 的行到达时已经结束、不会再长，所以 `createLineAccumulator` 收到时就切好，按字符占比分配时间，reducer 看到的都是短行。如果留到 reducer 再切，消息窗口只能在整行之间裁剪：短尾段（如 `Okay.`）会并入下一行的第一段，行边界就不再是句子开头，窗口要么裁断句子让它以新 id 重复进历史，要么一直不裁（复现：上限 120，400 行全部保留）。`trimToSentenceStart` 因此保持原样。

修复前 token 少，只是因为翻译中途就停了，不代表更省。按 token 计费时，每个请求约 640 个输入 token，大头是 system prompt 和上下文，所以成本主要看请求频率。按字符计费的 DeepL 直接受益（见 §4）。

译文抽查：段落切在句中时，模型靠上下文能接上（`…只要他们离开时是带着计划的` / `之后还会回来。…`）。`qwen-mt-*` 和 DeepL 没有上下文，切在句中的效果未验证。

## 6. 已知限制

- 真机用的是上游 WLK 0.2.26 + mlx-whisper，不是 Windows 上的 fork + faster-whisper。fork 的行结束与裁剪逻辑未核对；`PROGRESS.md` 记录的症状（1 行 3543 字符）一致。
- 百炼与 Chrome 识别路径只有单测，没有真机验证。
- server 模式不切（§2）。
- 第一段被短行合并、且这一行之后又被裁剪时，那一段可能在历史里部分重复一次。需要同时满足：前面有短行、连续讲话超过保留时长。
- 强切会让当前行回退最多约 70 字符，这一行要重译一次。
